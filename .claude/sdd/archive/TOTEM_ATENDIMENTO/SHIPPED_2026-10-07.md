## 1. O que foi entregue

Um totem de autoatendimento para lanchonete, para uma demonstração de oficina, que sobe com um único `docker compose up`, sem login e sem etapa de build no frontend.

| Tela | Para quem | O que faz |
|---|---|---|
| `/totem` | Cliente (1080x1920, toque) | "Toque para começar", cardápio por abas, carrinho, **revisão do pedido**, confirmação com número de 3 dígitos |
| `/cozinha` | Atendente | Fila em ordem de chegada; Iniciar, Marcar pronto, Entregar e Cancelar |
| `/painel` | TV (1920x1080) | Preparando e Pronto; destaque de 6 s e voz "Pedido N, pronto"; tempo médio de preparo |
| `/` | Operador | Links para as três telas |

Stack: FastAPI, SQLAlchemy 2 (síncrono) com psycopg 3, PostgreSQL 16, HTML com Tailwind via CDN e JavaScript puro, pytest.

## 4. Lições aprendidas

### 4.1 Técnicas

| Lição | Detalhe |
|---|---|
| `SKIP LOCKED` sozinho não impede o duplo avanço | Se a segunda requisição chega depois do commit da primeira, não há trava e o pedido pularia dois estados. O corpo de `avancar` passou a levar `from_state`, e um estado desatualizado devolve 409 |
| Contador diário precisa de upsert, não de `SELECT FOR UPDATE` | No primeiro pedido do dia não existe linha para travar. `INSERT ... ON CONFLICT DO UPDATE ... RETURNING` cobre o caso e não deixa buracos na numeração |
| `FOR UPDATE` com relacionamento em `JOIN` externo falha no PostgreSQL | O relacionamento de itens usa `lazy="selectin"` |
| "Ordem de chegada" é `id`, não `created_at` | O `id` nasce depois de travar o contador, então acompanha o número do pedido |
| O preflight do Tailwind via CDN sobrescreve estilos de `html` e `body` | Os estilos de base usam `body.tela-*`, que têm especificidade maior |
| Modificadores de opacidade do Tailwind não funcionam com `var()` | Cores do design system via variáveis CSS; teste automático proíbe hexadecimal fora de `tokens.css` |
| Voz do navegador exige gesto do usuário | O painel mostra "Toque para ativar o som"; sem toque, o destaque visual continua funcionando |

### 4.2 Processo

| Lição | Detalhe |
|---|---|
| Ler o design system inteiro antes de desenhar compensou | Trouxe o rodapé de tempo médio, o destaque de 6 s e a lista de itens sempre visível, que o DEFINE não cobria |
| Teste de mutação vale o custo | 64 testes passando de primeira geravam desconfiança. Quebrar o código de propósito mostrou que a suíte pega os erros certos |
| Verificar a aplicação rodando acha o que o pytest não acha | Os testes de interface em navegador confirmaram tempos de 8 s e 30 s, voz e conflitos 409 |
| Teste de interface também tem corrida | Uma verificação do 409 falhou por depender do polling de 2 s. Foi consertada servindo a lista antiga à cozinha |
| Registrar os ajustes ao DEFINE no DESIGN (seção 1.4) manteve a rastreabilidade | |

### 4.3 Comunicação

| Lição | Detalhe |
|---|---|
| Descrição de opção de pergunta tem de ser coerente | Na tela de revisão, a opção escolhida dizia que a lista de itens sairia do cardápio, o que impediria diminuir ou remover item. Foi mantida a lista no cardápio e a revisão ficou só de leitura |

### 4.4 Ferramentas

| Lição | Detalhe |
|---|---|
| Templates do SDD não existiam no repositório | Os documentos seguiram a estrutura descrita nos comandos |
| Playwright MCP ocupado por outro Chrome | Foi usado um Chromium isolado com o `playwright-core` já instalado, sem encerrar o processo alheio |
| `npm install` travou na rede | Resolvido reaproveitando um `playwright-core` já presente na máquina |
